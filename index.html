Georeferenced Gaussian Splatting Pipeline

Raw drone imagery → browser-viewable 3D Tiles at true lat/lon/elevation
Sole developer · production

Commercial photogrammetry tools produce georeferenced output but lock the process behind a closed pipeline. I rebuilt that capability end-to-end with open tooling so every stage stays inspectable and the accuracy is measurable rather than asserted.

The hard part isn't the reconstruction — it's the coordinate math between stages. Structure-from-Motion solves camera poses in an arbitrary local frame with arbitrary scale. Getting that into real-world coordinates means fitting solved camera centers to EXIF GPS with a similarity transform, landing in a local ENU frame in true meters, and only then training the splat model so the output is metrically meaningful.

Outcome
  • 0.107 m horizontal GPS residual across 119 of 120 solved cameras on a target capture subset
  • 0.24 m 3D georeferencing RMSE, exposed in-app as a per-reconstruction QA readout so field users see confidence, not just geometry
  • Diagnosed placement failures traced to WGS84 ellipsoidal height vs. MSL/geoid offsets and terrain-height correction — a class of bug that silently puts models tens of metres off vertically
  • Compressed a 109k-Gaussian scene to a ~7.4 MB PLY for practical browser delivery
On the numbers above
  • Both figures are camera-prior fit residuals — they measure how well solved cameras agree with the GPS priors they were fitted to. That is not the same as independent accuracy against surveyed checkpoints withheld from the fit, and the tooling stamps every output with that caveat rather than letting the distinction blur.
  • Consumer GPS priors are metre-level at best; RTK or surveyed ground control should replace them where available, and the pipeline is built to accept that substitution.

From the alignment tool

The geodesy is written out rather than delegated to a library — geodetic to ECEF on the WGS84 ellipsoid, then ECEF to a local ENU frame via the rotation matrix at the scene origin:

def geodetic_to_ecef(lat_deg: float, lon_deg: float, h: float) -> np.ndarray:
    # WGS84 ellipsoid.
    a = 6378137.0
    f = 1.0 / 298.257223563
    e2 = f * (2.0 - f)
    lat, lon = math.radians(lat_deg), math.radians(lon_deg)
    sin_lat, cos_lat = math.sin(lat), math.cos(lat)
    n = a / math.sqrt(1.0 - e2 * sin_lat * sin_lat)
    return np.array([
        (n + h) * cos_lat * math.cos(lon),
        (n + h) * cos_lat * math.sin(lon),
        (n * (1.0 - e2) + h) * sin_lat,
    ], dtype=np.float64)


def ecef_to_enu_matrix(lat_deg: float, lon_deg: float) -> np.ndarray:
    lat, lon = math.radians(lat_deg), math.radians(lon_deg)
    sin_lat, cos_lat = math.sin(lat), math.cos(lat)
    sin_lon, cos_lon = math.sin(lon), math.cos(lon)
    return np.array([
        [-sin_lon,            cos_lon,           0.0],
        [-sin_lat * cos_lon, -sin_lat * sin_lon, cos_lat],
        [ cos_lat * cos_lon,  cos_lat * sin_lon, sin_lat],
    ], dtype=np.float64)

3D Inspection & Compliance Viewer

Turning a photoreal capture into pass/fail engineering answers
Sole developer · production

A photoreal 3D scene looks impressive and answers nothing. The value is in measurement. I built a browser viewer that takes Gaussian splat scenes and returns the specific determinations inspection crews actually need — vegetation clearance compliance, structural clearances, and dimensional analysis — with the result attached to the geometry rather than to a clipboard.

For vegetation work the viewer segments a clicked object, computes its minimum height above the ground plane, compares against a configurable threshold, and reports pass/fail with the measured value and a visualized clearance plane. A separate mode slices the scene at 1.3 m for diameter-at-breast-height, clusters trunk cross-sections, and classifies each into fire fuel size classes under the NFFL system.

An early approach tinting individual splats via the renderer's RGBA buffer produced no visible result; I pivoted to generating explicit 3D marker geometry at detected features, which also made the classifications selectable and inspectable rather than merely visual.

Capabilities Shipped
  • Clearance-violation detection with configurable thresholds and pass/fail visualization
  • DBH slice analysis at 1.3 m with automatic trunk clustering
  • Fuel size classification (1h / 10h / 100h / 1000h) driven by measured diameter
  • Point-to-point measurement and 3D segmentation backed by a Python ML service

Human-in-the-Loop Gaussian Classification

Teaching a classifier the categories that matter operationally
Sole developer · production

Unsupervised clustering labels a scene exhaustively and arbitrarily — it finds the classes the data suggests, not the classes an inspector needs. I built a supervised path where an operator corrects labels through a QA pass and the classifier learns the domain-meaningful categories from those corrections.

The clearest evidence it works: during QA I created a dead vegetation class that no unsupervised cluster had ever produced. It matters operationally — dead vegetation is a fire-risk signal — and it only exists because a human with domain knowledge put it there. That's the whole argument for supervision in one example.

Outcome
  • Supervised labels applied across a 1.3M-Gaussian production scene
  • 72% supervised coverage vs. 99% unsupervised — the honest tradeoff; supervision only labels what it has been taught, and iterative re-QA closes the gap
  • Classified features exported as 3D Tiles and GeoJSON for use in standard GIS tooling
  • Re-ran at roughly 3× Gaussian density with supervised labels reapplied to test stability under densification

LiDAR Processing & Multispectral Sensor Integration

Field data engineering — point clouds, reprojection, sensor SDKs
Sole developer

Reconstruction work only matters if the upstream data is correctly conditioned. I built PDAL pipelines converting raw LiDAR into cloud-optimized point cloud (COPC) format with reprojection into projected coordinate systems for analysis, so large point clouds stream efficiently instead of requiring a full download.

Separately, I developed and validated a Windows SDK capture workflow for a multispectral imaging sensor — sensor integration, capture-mode configuration, and processed-output review feeding vegetation analysis. Field-side, I authored repeatable capture standards covering obstacle clearance, height tiers, image overlap, GSD targets, RTK, and lighting consistency, which is what makes reconstructions comparable across flights instead of one-off.

SnowTracker — Price Intelligence Platform

Full-stack product · ~19k lines of backend Python · 33 retailer integrations
Personal project · sole developer

A price-tracking platform for snowboard equipment across 33 independent retailers. Built because the market is fragmented across small shops running Shopify variants with no common catalog format, and no aggregator covered them.

The engineering problem isn't scraping — it's identity resolution. The same board appears across dozens of storefronts under inconsistent titles, so the schema separates products from offers: one canonical product, many retailer offers. A heuristic classifier normalizes titles and URLs into category, equipment type, and brand to drive that matching. Wayback Machine integration backfills price history for products that existed before tracking started.

Architecture
  • Next.js frontend proxying API calls through a route handler to a Flask backend, SQLite for storage
  • 33 retailer-specific catalog ingestion scripts over Shopify and custom storefronts
  • Normalized products/offers schema so one item's price can be compared across sellers over time
  • Money stored as integer cents throughout — never floats
  • Token-protected admin surface; public browsing needs no account
